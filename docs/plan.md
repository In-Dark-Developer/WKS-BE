## 0. V1에서 바뀌는 것 한 줄 요약

1차 릴리즈는 "사주"와 "소개팅 사전신청"이 분리된 구조였다.
V1은 **사주 결과 페이지가 홈**이 되고, 궁합지도·소개팅이 하단 네비로 붙는다.
로그인(카카오)은 **기록 저장·복원**과 **소개팅**에서만 요구한다.

```
티저(최초 1회, 네비 없음)
 ├─ 내 사주 보기 → 입력 → 로딩 → 사주 결과 = 홈
 └─ 새로운 인연 찾기 → 소개팅 flow

홈(네비 있음): 홈 / 궁합지도 / 새로운 인연

공유 링크 진입(네비 없음)
 → 초대 티저 → 신규: 입력 / 기존: 불러오기 or 새로 작성
 → 친구 궁합 생성 → 궁합 결과 → "내 사주 내용도 확인하기" → 홈(네비 켜짐)
```

## 1. 확정된 설계 결정

### 1.1 로그인 전후 데이터 처리 — 계정 우선

**계정에 저장된 결과가 항상 우선하고, 로그인 시 계정 결과가 복원된다.**

| 상황 | 처리 |
|---|---|
| 브라우저 결과 O · 계정 비어 있음 | 브라우저 결과를 계정에 연결 (`result.member_id` 채움) |
| 브라우저 결과 O · 계정 결과 O | **계정 결과 복원.** 브라우저 결과는 삭제하지 않고 방치 |
| 브라우저 결과 X · 계정 결과 O | 계정 결과 복원 |
| 둘 다 없음 | 사주 입력으로 유도 |

- 병합(두 결과의 친구 궁합 합치기)은 **V1에서 하지 않는다.** V2 과제
- 브라우저 결과는 계정 결과가 있을 때 **삭제하지 않는다** (데이터 손실 방지)
- 대부분의 유저는 첫 번째 케이스다. 로그인이 V1에서 처음 생기는 기능이기 때문
- 계정당 결과는 **1개**다. `result.member_id` 에 부분 UNIQUE 를 건다 (2026-09-21)

### 1.2 궁합 상세 이유 — LLM, 최초 열람 시 생성

- 생성 시점: 궁합 등록 시가 **아니라** 상세를 **처음 열어볼 때**
- 생성 결과는 DB에 캐싱. 재조회 시 LLM 호출 0회
- 생성 실패 시 해당 영역만 미노출 (화면 전체를 에러로 만들지 않는다)
- 소개팅의 "궁합 까닭"도 **같은 캐시를 재사용**한다 (해금 시점에 생성)
- 프롬프트에 생년월일·닉네임을 넣지 않는다. 팔자·점수·관계유형만

> 이유: 궁합 등록 즉시 생성하면 공유가 몰릴 때 호출이 폭증해 Gemini 무료 티어 429로 죽는다.
> 1일차 세대 주기 중간값이 6분이라 몰림이 실제로 발생한다.

### 1.3 인증 — 카카오 로그인, 회원번호만 사용

- 카카오 동의항목은 **아무것도 받지 않는다.** 회원번호(`id`)만 식별자로 사용
- 이름·연락처 등은 소개팅 신청 폼에서 직접 받는다
- `kakao_id` UNIQUE로 중복 계정·중복 신청을 차단
- 세션 토큰은 **JWT**다. 로그아웃·다중 기기 관리는 V1 에서 하지 않는다 (2026-09-21)
- 소개팅은 **학교 메일 재학 인증**이 필요하다 (2026-09-21 확정, 흐름상 위치는 `TBD-16`)

### 1.4 재화 "실"

| 획득 | 양 |
|---|---|
| 가입 기본 | 10 |
| 출석 체크 (1일 1회) | 5 |
| 내 궁합지도에 친구 1명 등록될 때마다 | 3 |
| 제휴처 배너 유입 | 제휴처별 설정값 |

| 소모 (정보 해금, 대상 1명당) | 양 |
|---|---|
| 사진 | 10 |
| 이름 | 7 |
| 학과 | 5 |
| 궁합 까닭 | 3 |
| **전체 해금** | **25** |

- **현금 결제(충전)는 V1 범위 밖.** 획득 경로는 위 표뿐
- 모든 증감은 원장(ledger)에 기록한다. 잔액 컬럼만 두지 않는다

## 3. 기능 명세 — 사주 입력

| ID | 기능 | 동작 | 예외·조건 |
|---|---|---|---|
| 2.1 | 사주 정보 입력 | 성별/달력 기준/생년월일/태어난 시간/닉네임. 필수값 완료 시 "점지 확인하기" 활성화 | 필수값 미입력 시 생성 불가 |
| 2.2 | 성별 | 남자/여자 중 하나 | 미선택 시 "성별을 선택해주세요" |
| 2.3 | 달력 기준 | 양력/음력 | 미선택 시 안내 |
| 2.4 | 생년월일 | `YYYYMMDD` 8자리 | 형식 오류·존재하지 않는 날짜 시 오류 문구, 입력값 유지 |
| 2.5 | 태어난 시간 | 시진 선택 | — |
| 2.6 | 시간 미상 | "태어난 시간을 몰라요" | 선택 시 기존 선택 시간 해제 |
| 2.7 | 닉네임 | 사주 카드·궁합지도 표시명 | **최대 8자**, 미입력 시 진행 불가 |
| 2.8 | 결과 생성 | 검증 → 계산 요청 → 로딩 → 결과 | **연속 클릭 중복 요청 방지** |
| 2.9 | 로딩 | 계산 중 로딩 화면 | 실패 시 오류 화면 |
| 2.10 | 입력 오류 | 해당 항목에 안내 | 정상 입력값 유지 |
| 2.11 | 네트워크/서버 오류 | 오류 안내 + 재시도 | 재시도 시 입력값 유지 |

> **2.7 닉네임 주의**: DB 컬럼(`result.nickname VARCHAR(20)`)은 **그대로 둔다.**
> 8자 제한은 입력 검증(DTO)에서만 건다. 기존 데이터에 9자 이상이 있어 DB를 줄이면 깨진다.
>
> **2.8 중복 요청 주의**: 1일차에 18초 안에 같은 사람이 3회 제출한 사례가 있다(재제출 16.7%).
> 프론트 버튼 비활성화 + 서버 측 방어 둘 다 필요.

## 6. 기능 명세 — 공유 링크 진입

| ID | 기능 | 동작 | 예외·조건 |
|---|---|---|---|

| 5.4 | 기존 판별 | "이전 정보 불러오기" / "새로 작성하기" 선택 | 조회 실패 시 새로 작성 가능 |
| 5.5 | 이전 정보 불러오기 | 재입력 없이 기존 데이터로 궁합 계산 | 유효하지 않으면 재입력 유도 |

| 5.7 | 친구 궁합 생성 | "내 운명을 친구 궁합 지도에 꿰기" | 실패 시 입력값 유지 + 재시도 |
| 5.8 | 궁합 기록 등록 | **결과 생성 완료 시점**에 공유자 지도에 추가 (링크 접속만으로는 X) | 중복 등록 방지 (아래 참조) |
| 5.9 | 궁합 결과 | 점수/인연 유형/해설 | 실패 시 데이터 유지 + 재시도 |
| 5.10 | 상세 이유 | "왜 나에게 귀인일까요?" / "둘이 만나게 된다면?" / "둘이 싸움이 난다면?" | 일부 없으면 그 영역만 미노출. LLM (1.2) |
| 5.11 | 친구 상세 | 지도·리스트에서 친구 선택 → 상세 | 실패 시 이전 화면 유지 |
| 5.12 | 내 사주 확인 | 일반 사주 결과 = 홈으로 이동 | 3장과 **동일 컴포넌트** |
| 5.13 | 잘 맞는 오행 | 홈과 동일하게 노출 | 별도 버전 만들지 않는다 |
| 5.14 | 네비 노출 | 홈 진입 순간부터 네비 O | **공유 flow 중에는 네비 없음** |
| 5.15 | 재공유 | 홈 → 궁합지도 → 공유 CTA | 취소·실패 시 현재 화면 유지 |
| 5.16 | 잘못된 링크 | 이용할 수 없는 링크 안내 | 홈 이동 경로 제공 |

> **5.8 중복 등록 기준**: `(origin_id, guest_id)` UNIQUE를 유지한다.
> 로그인 유저는 추가로 **같은 member_id가 같은 공유자 지도에 두 번 등록되지 않게** 막는다.
> (구현 방식은 `TBD-14` 확정 전까지 보류)
> 비로그인 유저가 "새로 작성하기"로 결과를 두 개 만드는 경우는 V1에서 막지 않는다.
>
> **5.8 실 지급**: 등록 완료 시 공유자에게 실 +3. `(member_id, reason, ref_id)` UNIQUE로 중복 지급 차단.

### 7.1 흐름

```
새로운 인연 탭
 → 로그인 안 됨 → 카카오 로그인
 → 소개팅 프로필 없음 → 신청 모달 (사진·이름·학과·연락처·MBTI·자기소개)
 → 와쿠와쿠 로딩
 → Top 3 카드 (일부 정보 블러)
 → 실로 정보 해금 → 실 부족 시 "운명의 실 구매하기"
 → 실 보내기(매칭 요청, 실 차감 없음) → 확인 모달 → 완료
요청 보관함: 나한테 보낸 사람 / 내가 보낸 사람 → 수락·거절 → 연락처 공개
```

|---|---|
| 기본 공개 | 자기소개, 궁합 점수, MBTI |
| 해금 필요 | 사진, 이름, 학과, 궁합 까닭 |
| 매칭 성사 시 공개 | 연락처 |

### 7.3 추천·매칭 규칙 (2026-09-24 확정)

- 소개팅 신청자 중 **이성**만 대상으로 기존 `CompatibilityCalculator` 점수 내림차순으로 최대 3명을 추천한다. 같은 학과 제외나 추가 가중치는 없다. 친구 궁합 기록을 만들지 않는다.
- 한 번 추천 카드에 나온 사람은 리롤 이후 다시 추천하지 않는다. 새로 신청한 사람은 다음 선정 시 후보에 포함한다. 추천 이력과 현재 표시 중인 후보는 회원별로 저장한다.
- 매칭이 성사되어도 두 사람 모두 소개팅을 계속 이용하고 추천 후보에 남는다. 다른 사람에게도 요청하거나 요청받을 수 있다. 받을 수 있는 요청 수에는 상한이 없다.
- 요청이 수락되면 연락처는 양쪽에 공개한다.
- 소개팅 카드의 "궁합 이유"는 친구 궁합 이유와 **다른 문구**다. 해금 시 처음 만들고 소개팅 전용 캐시에 보관한다. 추천 점수만 계산하는 동안에는 LLM을 호출하지 않는다.

## 8. API 초안

인증: JWT, HttpOnly 쿠키로 전달 (2026-09-21 JWT 확정, 2026-09-25 Bearer 헤더에서 쿠키로 전환). 공통 응답 포맷은 `docs/api-spec.md`를 따른다.

### 8.1 인증

| 메서드 | 경로 | 설명 |
|---|---|---|
| `POST` | `/api/auth/kakao` | `{code, redirectUri, resultId?, ref?}` → 토큰 발급 + 1.1 규칙으로 결과 연결/복원 + 제휴 보상 |
| `GET` | `/api/me` | 로그인 상태, 결과·프로필 보유 여부, 실 잔액 |
| `GET` | `/api/me/result` | 내 결과 조회. 계정에 연결된 결과를 `GET /api/results/{resultId}` 와 같은 구조로 반환, 없으면 404 (2026-09-21 추가) |

```json
// POST /api/auth/kakao 응답
{
  "token": "...",
  "isNewUser": true,
  "restoredResultId": "3f2a...",
  "rewardGranted": { "partnerName": "OO", "amount": 10 }
}

// GET /api/me
{ "memberId": 12, "hasResult": true, "hasDatingProfile": false, "threadBalance": 10 }
```

- `restoredResultId`: 계정 결과가 복원된 경우 그 id. 프론트는 브라우저 저장값을 이걸로 교체한다
- `resultId` (2026-09-21 추가): 브라우저에 저장된 결과 id. 1.1 규칙의 연결·복원에 쓴다. 없거나 존재하지 않아도 로그인은 성공한다
- 브라우저 결과를 계정에 연결한 경우 `restoredResultId` 는 `null` 이다 (복원할 것이 없다) (2026-09-21 추가)
- `rewardGranted`: 없으면 `null`
- `ref`(제휴 코드)가 잘못돼도 **로그인은 성공**해야 한다. 조용히 무시

### 8.2 사주·궁합 (변경분)

| 메서드 | 경로 | 설명 |
|---|---|---|
| `GET` | `/api/results/{resultId}/element-match` | 잘 맞는 오행 + 이유 (3.5) |
| `GET` | `/api/compatibilities/{id}/reason` | 궁합 상세 이유. **없으면 이 시점에 LLM 생성 후 캐싱** (1.2) |

> `{id}` 는 순번(BIGSERIAL)이다 (2026-09-21 수용). 열거하면 남의 궁합 이유를 읽거나 LLM 생성을 유발할 수 있다. 호출 총량은 `CallBudget` 이 막는다 (초과 시 `LLM_UNAVAILABLE`).

## 9. 반드시 지킬 구현 원칙

### 9.1 블러는 서버에서 처리한다 (가장 중요)

해금되지 않은 필드는 **응답에 값을 넣지 않는다.** `locked: true`만 내려준다.

프론트에서 CSS로 흐리게만 처리하면 개발자도구로 이름·사진이 전부 보인다.
그러면 재화 구조가 무너지고, **동의 없는 개인정보 노출**이 된다.

### 9.2 사진 URL을 추측 불가능하게

- 잠긴 상태에서는 **원본 사진 URL을 내려주지 않는다**. 서버가 생성한 저해상도 블러 썸네일의 임시 조회 URL만 추천 카드에 내려준다 (2026-09-25 결정)
- 해금 후에도 순번 파일명이나 공개 버킷의 예측 가능한 경로를 쓰지 않는다
- 인증을 거치는 경로 또는 서명된 임시 URL로 제공한다

### 9.3 식별자를 노출하지 않는다

- `candidateId`는 `member_id`를 그대로 쓰지 않는다. 불투명한 값(UUID 등)을 쓴다
- `resultId`를 UUIDv4로 한 것과 같은 이유: 순번이면 남의 프로필을 열거할 수 있다

### 9.4 실은 원장으로 관리한다

```
thread_ledger(member_id, amount, reason, ref_id NOT NULL, created_at)
reason: SIGNUP_BONUS | CHECK_IN | MAP_FRIEND | PARTNER | UNLOCK | REQUEST | REROLL
UNIQUE (member_id, reason, ref_id)   -- 중복 지급·차감 방지

-- ref_id 는 NOT NULL (2026-09-21). NULL 이면 UNIQUE 가 중복을 못 막는다 (Postgres 는 NULL 끼리 다르다고 본다)
-- ref_id 값: SIGNUP_BONUS = member id / CHECK_IN = KST 날짜(yyyy-MM-dd) / MAP_FRIEND = compatibility id / PARTNER = 제휴 코드
--            UNLOCK·REQUEST·REROLL 은 소개팅 명세 확정 시
```

잔액은 원장 합계로 계산하거나, 잔액 컬럼을 두더라도 **원장과 같은 트랜잭션**에서 갱신한다.
"왜 실이 줄었냐" 문의에 원장으로 답할 수 있어야 한다.

### 9.5 동시성

해금·요청·출석은 **DB 제약(UNIQUE)으로 막는다.** 애플리케이션 로직의 "이미 있는지 조회 후 삽입"만으로는 동시 요청에서 뚫린다.
